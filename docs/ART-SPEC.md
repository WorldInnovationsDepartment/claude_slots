# Claude Slots — Final Art Spec

**Base design:** #0 "Classic Vegas" (winner, 71/80). **Grafted in from the judging round:** the payline block-bar marker and outcome-first RNG algorithm from #1 "Retro Terminal / Synthwave" (66/80), and the Claude-Code-concept symbol semantics + canonical-reel-strip neighbor logic from #2 "Claude-themed" (26/80, but praised for its concept mapping). Every frame below was generated by a small Python script (`gen.py` / `frames_lib.py` / `build_spec.py`, included alongside this file) that builds each line from fixed-width primitives and asserts every frame is a true rectangle before it is allowed into this document — nothing here is hand-typed ASCII art. Implementers should treat these as golden frames and diff their own renderer's output against them.

This spec assumes the shared frame model used by all three source designs: **a grid of `{glyph, fg, bold, dim}` cells**, driving two renderers — an in-TUI element tree (Tier 1, 8–12fps) and a raw-ANSI status line (Tier 2, 1fps). The outcome is always decided *before* rendering begins (§4); every phase is a deterministic function of that outcome plus elapsed time, so both renderers, at any fps, are just sampling the same state machine at different rates.

## 1. Symbol set & Claude Code semantics

The Vegas glyph set is kept almost entirely intact (per the winning design), with exactly two semantic changes: the digit `7` is retired in favor of `✻` (the Claude asterisk — literally Claude Code's own default spinner glyph, disclosed by design #2 as single-width in every terminal font tested) as the new top/jackpot symbol, and `★` stops being a generic "wild" and becomes a specific Claude Code concept like the other five mid symbols. This is the minimal graft that turns a generic fruit machine into *this* fruit machine.

| Glyph | Name | Claude Code concept | Tier | Dressing weight (of 100)\* |
|---|---|---|---|---:|
| `✻` | CLAUDE | The assistant itself — the top symbol, U+273B, sanctioned single-width exception (matches Claude Code's own spinner) | Top | 1.2 |
| `◆C◆` | MEDALLION | Claude's signature — a completed, clean turn. Special rarity tier, sits **between** JACKPOT and TRIPLE | Special | 0.3 |
| `BAR` | TOOL | An active/loaded tool call | High | 7.0 |
| `★` | TEST | A passing test / green check | High | 3.5 |
| `♦` | DIFF | A code diff / edit | Mid-high | 24.0 |
| `♣` | FILE | A file read/write | Mid | 20.0 |
| `☼` | TOKEN | A token — also literally the credit/coin glyph used in coin-rain | Mid-low | 14.0 |
| `♥` | PROSE | Creative/explanatory prose generation | Low | 30.0 |

\* Dressing weight governs only the **cosmetic** SPINNING blur mix and is baked into the canonical reel strips (§3) — it is deliberately decoupled from outcome probability (§2), exactly as both source designs #1 and #2 specify: pick the outcome first, then paint reels to match; never derive odds from per-symbol weights.

All eight glyphs are confirmed single-width (`unicodedata.east_asian_width` ∈ {Na, N, A}; verified programmatically over every frame in this document, see §7) and fall inside the render-constraint allowlist: box drawing, block elements, geometric shapes, `★ ☆ ♦ ◆ ● ✻ ✦`, digits/letters. No emoji in the default theme (§14 covers the opt-in emoji theme).

## 3. Canonical reel strips & neighbor table

Three reels, three *different-length* circular strips (20–24 stops), built once, hard-coded, never regenerated at runtime. Each strip is a concatenation of laps around one master symbol cycle — `✻ → BAR → ★ → ☼ → ♣ → ♦ → ♥ → ◆C◆ → (loops)` — where common symbols get extra laps (to bias SPINNING-blur/dressing frequency per §1's weight column) while the four rare/special symbols (`✻`, `BAR`, `★`, `◆C◆`) appear with identical counts on every reel. This single construction rule is what makes reels differ in *length and common-symbol density* while sharing one universal, deterministic neighbor table.

```
Reel 1 (22 stops): ✻ BAR ★ ☼ ♣ ♦ ♥ ◆C◆ BAR ☼ ♣ ♦ ♥ ☼ ♣ ♦ ♥ ♣ ♦ ♥ ♥ ♥
Reel 2 (24 stops): ✻ BAR ★ ☼ ♣ ♦ ♥ ◆C◆ BAR ☼ ♣ ♦ ♥ ☼ ♣ ♦ ♥ ♣ ♦ ♥ ♣ ♦ ♥ ♥
Reel 3 (20 stops): ✻ BAR ★ ☼ ♣ ♦ ♥ ◆C◆ BAR ☼ ♣ ♦ ♥ ☼ ♣ ♦ ♥ ♦ ♥ ♥
```

Symbol counts per reel (sum = strip length): `✻`×1, `BAR`×2, `★`×1, `◆C◆`×1 on every reel; `☼`×3 on every reel; `♣`/`♦`/`♥` vary — Reel1 `♣`4 `♦`4 `♥`6, Reel2 `♣`5 `♦`5 `♥`6, Reel3 `♣`3 `♦`4 `♥`5.

**Neighbor rule:** for a given reel, each symbol's canonical neighbor is read off its *first occurrence* on that reel's strip: `NEXT(sym) = strip[(firstIndex(sym) + 1) mod length]`, `PREV(sym) = strip[(firstIndex(sym) − 1) mod length]`. Because the four rare symbols are laid out identically at the head of every reel's strip, this table comes out **identical across all three reels** — one static lookup table, no per-reel branching needed at runtime:

| Symbol | NEXT (row below payline / near-miss forward neighbor) | PREV (row above payline) |
|---|---|---|
| `✻` CLAUDE | `BAR` | `♥` PROSE |
| `BAR` TOOL | `★` TEST | `✻` CLAUDE |
| `★` TEST | `☼` TOKEN | `BAR` TOOL |
| `☼` TOKEN | `♣` FILE | `★` TEST |
| `♣` FILE | `♦` DIFF | `☼` TOKEN |
| `♦` DIFF | `♥` PROSE | `♣` FILE |
| `♥` PROSE | `◆C◆` MEDALLION | `♦` DIFF |
| `◆C◆` MEDALLION | `BAR` TOOL | `♥` PROSE |

This table is what makes the cabinet feel mechanically real even at rest: **row above a payline symbol is always its `PREV`, row below is always its `NEXT`** — e.g. a `✻✻✻` payline *always* shows `♥ ♥ ♥` above and `BAR BAR BAR` below, in every idle frame, every JACKPOT frame, forever (see the JACKPOT storyboard, §8.7 — this is not coincidence, it is §4 step 3 applied literally).

## 4. RNG algorithm (outcome-first, seeded, unit-testable)

**Do not spin three independent reels and hope the probabilities fall out right.** Pick the outcome class first, resolve the payline to match it, then derive the two dressing rows purely from §3's static neighbor table (no further randomness). This is the same architecture all three source designs converged on, and it is what makes the whole system trivially unit-testable: given a seed, the output is fixed forever.

```
function spin(seed):
    rng = mulberry32(seed)                 # any seeded PRNG returning floats in [0,1)

    outcomeClass = rollOutcomeClass(rng)   # step 1 — consumes exactly 1 rng() call
    payline      = resolvePayline(outcomeClass, rng)   # step 2 — consumes 0-3 rng() calls
    grid         = fillNonPaylineRows(payline)         # step 3 — PURE, no rng() calls
    frame        = render(grid, outcomeClass)          # step 4

    return frame

function rollOutcomeClass(rng):
    r = rng()
    table = [ (JACKPOT, .015), (MEDALLION, .025), (TRIPLE, .080),
              (DOUBLE, .260), (NEAR_MISS, .120), (LOSE, .500) ]
    acc = 0
    for (class, p) in table:
        acc += p
        if r < acc: return class
    return LOSE   # floating-point fallback, never reached if table sums to 1.0

function resolvePayline(class, rng):
    switch class:
      case JACKPOT:    return [CLAUDE, CLAUDE, CLAUDE]
      case MEDALLION:  return [MEDALLION, MEDALLION, MEDALLION]
      case TRIPLE:
          tier = weightedPick(rng, TRIPLE_TIERS)     # BAR .010 TEST .010 TOKEN .012
                                                      # FILE .015 DIFF .016 PROSE .017 (of .08)
          return [tier, tier, tier]
      case DOUBLE:
          tier   = weightedPick(rng, DOUBLE_TIERS)   # CLAUDE .010 BAR .010 TEST .020 TOKEN .030
                                                      # FILE .045 DIFF .065 PROSE .080 (of .26)
          oddPos = floor(rng() * 3)                  # which of the 3 reels is the odd one out
          filler = uniformPick(rng, ALL_SYMBOLS - {tier, MEDALLION})
          line = [tier, tier, tier]; line[oddPos] = filler
          return line
      case NEAR_MISS:
          # near-miss symbol choice is deliberately biased toward the rarer/flashier
          # symbols (the well-documented "near-miss effect") -- it does NOT reuse the
          # dressing weights from §1.
          sym = weightedPick(rng, NEARMISS_WEIGHTS)  # CLAUDE .30 MEDALLION .20 BAR .15 TEST .12
                                                      # TOKEN .10 FILE .06 DIFF .04 PROSE .03
          return [sym, sym, NEXT(sym)]               # reel 3 is always the "off" reel (see §5)
      case LOSE:
          loop:
              [a, b, c] = [uniformPick(rng, ALL_SYMBOLS) for _ in range(3)]
              if len(set([a,b,c])) == 3 and not looksLikeNearMiss(a,b,c):
                  return [a, b, c]                   # reroll on accidental match/near-miss shape

function fillNonPaylineRows(payline):               # NO randomness -- pure function of payline
    above = [ PREV(s) for s in payline ]             # row rendered above the payline
    below = [ NEXT(s) for s in payline ]             # row rendered below the payline
    return { above, payline, below }
```

**Unit-test shape:** because `fillNonPaylineRows` is pure and `resolvePayline`/`rollOutcomeClass` are the only calls that touch `rng`, a test can assert the full 3×3 grid for a fixed seed with zero mocking. Worked examples from a reference `mulberry32` implementation (included in `build_spec.py`), so implementers can cross-check their own PRNG port against these exact numbers:

```
seed=    257  class=JACKPOT     payline=[CLAUDE,CLAUDE,CLAUDE]  above=[PROSE,PROSE,PROSE]  below=[BAR,BAR,BAR]
seed=     45  class=MEDALLION   payline=[MEDALLION x3]          above=[PROSE,PROSE,PROSE]  below=[BAR,BAR,BAR]
seed=     25  class=TRIPLE      payline=[TOKEN,TOKEN,TOKEN]     above=[TEST,TEST,TEST]     below=[FILE,FILE,FILE]
seed=      7  class=NEAR_MISS   payline=[TEST,TEST,TOKEN]       above=[BAR,BAR,TEST]       below=[TOKEN,TOKEN,FILE]
seed=      1  class=DOUBLE      payline=[PROSE,FILE,PROSE]      above=[DIFF,TOKEN,DIFF]    below=[MEDALLION,DIFF,MEDALLION]
seed=      3  class=LOSE        payline=[TOKEN,TEST,BAR]        above=[TEST,BAR,CLAUDE]    below=[FILE,TOKEN,TEST]
```

Any conforming `mulberry32(seed)` port that reproduces these six rows for these six seeds has a correct implementation of §2's probability table and §3's neighbor table simultaneously.

## 5. Near-miss rule & the overshoot beat

**The deterministic rule:** a NEAR MISS payline is always `[S, S, NEXT(S)]` — reels 1 and 2 land on the same symbol `S`, reel 3 (always reel 3, never 1 or 2) lands on `S`'s fixed forward neighbor from §3's static table. There is no fuzziness here: "one step off" means exactly one entry in one static lookup table, the same table that drives the dressing rows, so a near miss is never a coincidence of independent RNG rolls — it is deliberately constructed to be exactly one reel-strip position away from a real win.

**The overshoot beat** (grafted from design #0, extended with the deterministic rule above): during STOPPING, once reels 1 and 2 have locked on `S`, reel 3's final deceleration briefly **overshoots** — it shows `S` for one frame (completing an illusory `SSS`), then snaps one stop further along its strip to the true, settled `NEXT(S)`. This is a single extra ~80ms frame inserted between "reel 3 still blurred" and "reel 3 locked" — see §8.5 for the literal frames (`★ ★ ★` flashing for one frame, then settling to `★ ★ ☼`).

## 6. Hot-state rule (indivisible)

**One rule, always applied together, never one without the other:** a matched/winning reel cell switches its box from the single-line set (`┌─┐│└┘`) to the double-line set (`╔═╗║╚╝`) **and** its glyph renders bold, at the same instant, as one atomic state change. A terminal with no bold support still reads "hot" correctly from the glyph swap alone; a terminal that can't render box-drawing doubles (rare) still reads "hot" from the bold weight. Never emit bold without the double-line swap, and never swap to double-line without also setting bold — a renderer that did either alone would be implementing half a rule.

This applies **per reel-cell-column** (all three symbols in a hot reel's box go double/bold together, not just the payline cell) and only ever to reel cells — the outer cabinet shell is always double-line `╔═╗║╚╝╠╣` regardless of state (it is the fixed chrome chassis); "hot" is expressed there only through the color table's hue shift (§9), never a glyph change. On a DOUBLE win only the matched two of three reel columns go hot; on TRIPLE/MEDALLION/JACKPOT, all three do.

## 7. Chassis art — STANDARD / COMPACT / GRAND

All three sizes share one anatomy: double-line chrome shell (`╔═╗║╚╝╠╣`) → marquee (bulb-chase flanking the wordmark) → separator → 5-row reel bay (box-top / dressing-above / **payline** / dressing-below / box-bottom, 3 reel cells each) → lever column pinned to the right → separator → 1-line info strip → bottom border. The payline row is always flanked by solid block bars `▐ … ▌` in place of the outer box wall — present in every size, every phase, hot or cold — so the active row never depends on color alone (graft #1, judge-mandated).

### 8.13 OUTCOME — ABORTED (user pressed Esc mid-spin)

Not present in any source design — the reel bank does not simply vanish; it visibly **brakes**: the blur pattern goes asymmetric/jittery for one frame (the mechanical "grinding to a halt" cue) before the reels settle on a neutral placeholder (`—`, not a real symbol — this spin produced no result and must never be mistaken for a LOSE). The 1-credit spin cost is refunded, since no outcome was ever resolved. This is the one storyboard deliberately shorter than the general 1.5-4s outcome-animation guidance: the user just pressed Esc specifically to stop waiting, so the machine must acknowledge that instantly (~0.6s total) rather than force them to sit through a padded animation — fast feedback is the correct UX for an interrupt, not a violation of the win/lose pacing rule. **Implementation note (deviation from the table above):** both renderers verifiably turn *any* `dim` span
into one flat `#999999` gray (see ARCHITECTURE.md §4's live-measured `dimColor` fact, and
`render-ansi.js`'s matching `DIM_GRAY` override) — there is no dimmed-but-still-tinted rendering available on
either tier. A literal `dim:true` on both `abortedText` and `errorText` would therefore make ABORTED and
ERROR collapse into the *same* indistinguishable gray as each other (and as every other dim role in this
table), which directly defeats this section's own "red = error, always unambiguous" rule. `lib/symbols.js`
keeps the exact hues above but drops `dim` for just these two roles so ERROR reads as red and ABORTED as
cool steel-gray, distinctly, everywhere they appear (marquee text, the JAM/MALFUNCTION brake-phase bulbs,
and the §12 transcript result line). Every other `dim` role in this table is unaffected.

## 10. Credits economy

- **Starting balance:** 100 credits.
- **Cost per spin:** 1 credit, deducted the instant the lever is pulled (LEVER PULL phase, not on reveal) — matches §8.2.
- **Payout timing:** credited the instant the outcome animation begins its counter tick (JACKPOT/MEDALLION/TRIPLE — see the progressive tick-up in §8.7-8.9), or instantly with no tick-up (DOUBLE — §8.10). NEAR MISS and LOSE pay 0.
- **Never blocks:** balance is never allowed to prevent a spin. If balance would go below 0 it floors at 0 and the machine keeps spinning for free.
- **ON THE HOUSE** (graft #8): at 0 credits, IDLE's info-strip text substitutes a comp banner (§8.1) in place of `CREDITS: 000 LAST WIN: NNN` — same loop, same bulbs, one text swap. Never a modal, never a separate screen, never a message the user has to dismiss.
- **ABORTED / ERROR refund:** because these two outcomes resolve no payline (§8.13-8.14), the 1-credit spin cost is refunded — the user is never charged for a turn the machine didn't actually complete.
- **Persistence:** implementation's call; nothing in this spec requires credits to survive a process restart, but nothing prevents it either.

These numbers are tuned for feel, not RTP — see §2's closing note on scaling payouts uniformly if a house edge is wanted.

## 11. 1 fps degradation notes (statusLine / Tier 2 target)

Core rule: **design for discrete states, not motion-blur continuity.** At 1fps you get one paint per second — every phase below is built so its single most important frame is guaranteed to land on at least one tick.

- **IDLE** — bulbs alternate once per tick rather than every 600ms; reads as a slow, calm blink, which suits attract-mode fine. ON THE HOUSE degrades trivially since it's just IDLE with different text.
- **LEVER PULL (§8.2)** — skip straight from "grip" (knob0) to "yank!" (knob4); drop the three mid-frames entirely. The credits-decremented number carries the meaning even without seeing the knob travel.
- **SPIN-UP (§8.3)** — collapses to a single "all reels now blurred" frame; the wind-up choreography is an 8-12fps-only flourish.
- **SPINNING (§8.4)** — render the steady-blur frame every tick, with the ticker as the only thing that must visibly change every tick. The speed-ease and glint-sweep sub-frames are dropped entirely at 1fps — skipping them costs nothing because the ticker already proves liveness.
- **STOPPING (§8.5)** — hold each of the 3 lock-steps for a minimum of 1 full second even though the 8-12fps renderer holds them for ~0.3s. The near-miss overshoot frame gets the same treatment: **hold it a full 1.0s minimum** rather than its native ~80ms, so a 1fps viewer actually gets to see the illusory triple before the snap — this is the one frame in the whole spec where the 1fps version is *more* visible than the 8-12fps original, deliberately, because it's the single highest-tension frame in the near-miss story.
- **REVEAL (§8.6)** — extend the ~300ms hold to ≥1.0s so the completed combo is guaranteed at least one visible paint before the outcome animation starts.
- **OUTCOME ANIMATIONS (§8.7-8.14)** — pick keyframes, don't tween. Paint the "flash"/marquee-change frame on tick 1, then jump the payout counter straight to its final value (an intermediate tick-up number that only ever paints once looks like a bug, not an animation), then hold the settled frame for any remaining ticks. Coin-rain / sunburst / brake-jitter decoration is dropped — the marquee text and the final number carry 100% of the information.
- **LOSE (§8.12)** — the 3-frame sequence compresses to two ticks: dim+wistful-mark on tick 1, relit-normal on tick 2.
- **ABORTED / ERROR (§8.13-8.14)** — each collapses to its 2 frames, one per tick (brake→settled). Never collapse to a single frame: a 1fps viewer must see the reel bank actually change state (brake→placeholder), not just appear with the final marquee already showing, or the "something happened mid-spin" read is lost.

General clamp: **any hold or transition spec'd under ~1.0s must be extended to a 1.0s minimum specifically in the 1fps renderer** (never in the 8-12fps one). That single rule keeps every phase legible at 1fps without a second design pass per phase.

## 12. Transcript result line (the permanent static record)

The TurnDuration slot's outcome animation runs for ~3-4s and then must resolve to a **compact 1-2 line static frame that stays in the transcript forever**. Format:

```
▐ {reel1} │ {reel2} │ {reel3} ▌ {LABEL} {payout} ✦ credits {balance} · {elapsed}s
```

One line per outcome class, literal:

```
▐ ✻ │ ✻ │ ✻ ▌ JACKPOT +250 ✦ credits 346 · 12s
▐ ◆C◆ │ ◆C◆ │ ◆C◆ ▌ SIGNATURE +77 ✦ credits 173 · 8s
▐ BAR │ BAR │ BAR ▌ TRIPLE +40 ✦ credits 136 · 5s
▐ ♥ │ ♥ │ BAR ▌ DOUBLE +1 ✦ credits 97 · 3s
▐ ★ │ ★ │ ☼ ▌ so close +0 ✦ credits 96 · 4s
▐ ♣ │ ★ │ ♦ ▌ no win ✦ credits 96 · 2s
▐ — │ — │ — ▌ INTERRUPTED ✦ credits 97 · 6s
▐ — │ — │ — ▌ ERROR ✦ credits 96 · 9s
```

The `▐…▌` payline marker survives all the way down to this single permanent line — the same visual grammar used in every animated frame is still legible in the one frame a user will scroll back to see days later. All eight lines above are comfortably under 50 columns; no wrapping risk even in a narrow transcript pane.

## 13. Width / alignment rules

1. **Declared widths are hard limits, not targets.** STANDARD = 60 cols (58 interior), well inside the 62-col ceiling. GRAND = 80 cols (78 interior) at exactly 11 rows, inside the 80-col/9-11-row ceiling. COMPACT ≤ 40 cols (2-line) or ≤ 36 (1-line ultra-compact), no border.
2. **Every bordered frame is a true rectangle**: every line — border, marquee, separators, body rows, info strip — contains exactly the declared column count, achieved by centering/padding against the *interior* width (declared width minus 2 border columns), never by hand-counting spaces. This document's frames were built by `frames_lib.py` and every single one passed `assert_rect()` before being written here (§7 opening note).
3. **Reel cells are fixed-width and glyph-agnostic**: 5-col interior STANDARD/COMPACT, 7-col GRAND. Every symbol string — `✻`, `♦`, `BAR`, `◆C◆` — is centered into that fixed width, never manually padded per symbol, so a symbol of any length up to the cell width never breaks alignment.
4. **The payline row is the only row carrying the `▐…▌` block-bar flank** (replacing the outer box wall character only — internal cell walls are untouched). Every other row reserves the same width for a normal wall character, so the reel bank never shifts horizontally between rows or frames.
5. **The lever column is a fixed single-glyph-wide vertical track**, 4 cols right of the reel bay (STANDARD/GRAND). Exactly one of its 5 rows shows the knob `●` at any instant; rows above it show the rod `│`; rows below show blank — a monotonic, easy-to-compute rule (§8.2).
6. **Marquee and info-strip content are each one logical line**, produced by centering (marquee) or left/right-justify with a computed gap (info strip) against the interior width — never against the full bordered width, never by hand-typed spacing.
7. **Only single-width glyphs appear inside a bordered cell.** Every glyph in this spec was checked with `unicodedata.east_asian_width()` and falls in {Na, N, A} — never {W, F}. CJK, most emoji, and combining marks must never appear in the default theme (§14 covers the opt-in exception).
8. **COMPACT is exempt from the equal-line-width rule** (no border to break) but not from the single-width-glyph rule or its own column ceiling — every COMPACT/ULTRA-COMPACT line independently satisfies ≤40/≤36 columns.
9. **GRAND is capped at 11 lines** — do not add a 12th line for flourishes; fold any additional flavor (like the `RECENT:` strip) into the existing info-strip line via left/right-justify, same technique as STANDARD.

## 14. Optional emoji theme (opt-in, never default)

An explicit theme flag may remap the eight default glyphs to emoji equivalents for terminals/users who want it. This must never be the default and must never silently change layout math — emoji are frequently double-width or variation-selector-dependent, so a naive swap would break every `assert_rect` guarantee in this document. If implemented, the safe approach is a same-cell-count swap validated per-target-terminal, not a blind glyph substitution:

| Default | Concept | Emoji (opt-in) |
|---|---|---|
| `✻` | CLAUDE | ✨ |
| `◆C◆` | MEDALLION | 🏅 |
| `BAR` | TOOL | 🔧 |
| `★` | TEST | ✅ |
| `♦` | DIFF | 📝 |
| `♣` | FILE | 📄 |
| `☼` | TOKEN | 🪙 |
| `♥` | PROSE | 💬 |

Ship this behind a theme flag only, default OFF, and re-verify rectangularity against the target terminal's actual emoji rendering width before enabling — do not assume the mapping above is drop-in safe everywhere.

## 15. Implementation notes

- One shared frame model — a grid of `{glyph, fg, bold, dim}` cells — drives both renderers. Tier 1 (in-TUI, 8-12fps, invalidate floor 100ms) consumes it as a `Box`/`Text` element tree; Tier 2 (statusLine, 1fps, raw ANSI) samples the same grid less often and never interpolates between frames (§11).
- The outcome is decided **before** rendering starts (§4) — "spinning" is a fixed-duration-or-model-duration animation over a grid whose final state is already known. This is what makes STOPPING's stagger, the near-miss overshoot, and REVEAL's exact combo trivial to implement and unit-test.
- Elapsed time and token count are the only two values that must update every tick of SPINNING without exception — the real "is this thing alive" signal; blur glints and bulb chases are texture on top.
- `esc to interrupt` is present in the info strip from LEVER PULL through STOPPING; it drops once REVEAL starts (the model has already finished) and is replaced by outcome-specific text.
- Golden-frame testing: every frame in this document is reproducible byte-for-byte by `frames_lib.py` — wire a test that renders each named frame and diffs it against the fenced block here; a mismatch is either a spec update that forgot to regenerate this document, or a renderer bug.
- Files alongside this spec: `frames_lib.py` (pure builders), `gen.py` (dumps every frame + a rectangularity/width-glyph audit), `build_spec.py` (assembles and writes this document). Regenerate with `python3 build_spec.py` (writes `FINAL-ART-SPEC.md` in the working directory).
